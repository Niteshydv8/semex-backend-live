## Layout
- **`semex/`** is the SOURCE. It has `build.sh`, `README.md`, and a `__SEMEX_API_URL__` placeholder (and `http://localhost:8001`) in `utils/server-client.js`.
- **`semex-build/`** is a GENERATED artifact — do NOT hand-edit it. `build.sh` wipes it and re-copies `semex/` on every run, so any manual edit there is silently lost on the next build.

## Build
Run from `semex/`: `./build.sh <API_URL> [--obfuscate]` (prod URL: `https://api.semxhitter.pw`). It:
1. `rm -rf semex-build` then copies `semex/*` into it (dotfiles NOT copied).
2. Strips `build.sh` + `README.md` from the build.
3. `sed`-injects `<API_URL>` over both `http://localhost:8001` and `__SEMEX_API_URL__` in `semex-build/utils/server-client.js`.
4. Optionally obfuscates, then zips the build-dir contents (manifest at zip ROOT) to the repo root as `semex-v<version>-plain.zip` (plain) or `semex-v<version>.zip` (obfuscated). Version is read from `manifest.json`.

**Why it matters:** the source vs build difference in `server-client.js` is intentional (placeholder vs injected URL) — it is NOT a drift bug, so never "sync" the two. The correct workflow is: edit `semex/` only, then rebuild. The zip the user loads must come from `build.sh` (or an already-injected `semex-build/`), or the extension points at a dead API URL.

## Obfuscation gotchas (from build.sh, MV3-safe profile)
- NEVER enable `--self-defending` or `--debug-protection` — both break Chrome MV3 service workers silently.
- NEVER enable `--transform-object-keys` — it mangles keys that end up in JSON payloads to the backend (e.g. `{telegramId, otp, fingerprint}`).
- `libs/` is excluded from obfuscation.

## Loading
Users load unpacked from the `semex-build/` folder (chrome://extensions → Developer mode → Load unpacked), or unzip the `-plain.zip` and load that folder. Mobile Chromium browsers (Kiwi/Yandex) load the unzipped folder the same way.
